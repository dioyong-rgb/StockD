# StockD 통합 재고·주문 관리 — 단계별 진행 계획

이 문서는 이전 전체 확장 로드맵의 사본이다. 기존 노션 재고관리 페이지의 장문은 2026-10-04 정리했으며 이 사본은 로컬 참고용으로만 보존한다. 초기 범위는 네이버 스마트스토어·쿠팡이며, 현재 정리는 [주제별 문서 안내](https://app.notion.com/p/3ef15a85fa868135ae78d2102a1ad7b1)를 따른다.

정리일: 2026-10-04 / Asia/Seoul. 원본 설계·공식 문서 검토일: 2026-10-03.

**현재 단계는 설계·검토 완료, 개발 착수 전입니다.** 실행 가능한 앱·DB·수집기·fixture는 아직 없습니다. API 키·계정별 승인·권한은 미확인이고 실제 쇼핑몰 API 호출, GitHub 업로드, macOS·Linux 실행 검증은 수행하지 않았습니다.

## 1. 프로젝트 목표와 확정 범위

스마트스토어, 쿠팡 판매자배송·로켓그로스, G마켓·옥션, 11번가의 상품·옵션 재고와 주문을 한 화면에서 조회합니다. 옵션별 내부 SKU로 채널 상품을 연결하고, 추후 다른 쇼핑몰을 추가할 수 있는 구조로 만듭니다.

- 첫 버전: 상품·옵션·재고·주문 조회, 취소·반품·교환 조회, SKU 연결, 연동 상태 및 알림.
- 쿠팡은 판매자배송과 로켓그로스를 모두 사용하되 배송 방식과 재고 의미를 구분합니다.
- 쇼핑몰 재고 수정, 가격 변경, 발송 처리, 주문 상태 변경 같은 외부 쓰기 기능은 첫 버전에서 제외합니다.
- 주문 상태 갱신은 조회한 값을 내부 DB에 반영하는 의미입니다.
- ERP/WMS 실제 보유 재고와 외부 이메일·메신저 전달은 별도 확장 항목입니다. 첫 알림은 앱 내부 이력과 미해결 알림을 기본으로 제안합니다.

### 개발 규칙

- TypeScript, Next.js 15, React 19, Tailwind CSS, shadcn/ui.
- Zustand, React Hook Form + Zod, PostgreSQL + Prisma, 별도 TypeScript 수집 워커.
- 한국어 응답·주석·문서·커밋 메시지, 영어 변수/함수명, 2칸 들여쓰기.
- any 타입 금지, 컴포넌트 분리·재사용, 반응형 필수.
- 현재 작업 OS는 Windows 11입니다. 같은 스택의 macOS·Linux 적용은 가능하지만 실제 환경 재현은 구현 후 검증합니다.

**병행 원칙:** S0의 ESM 신청 준비는 S1~S3와 병행합니다. 승인이나 키가 없어도 fixture와 S7 화면 개발은 진행할 수 있습니다. 실제 연동 완료는 키·권한·IP와 판매자센터 대조까지 확인한 채널/기능에만 표시합니다. S4~S6는 공통 기반 이후 계정 준비에 따라 병행 가능하고, S9·S10도 승인 상황에 따라 서로 병행할 수 있습니다.

## 4. 설계에서 지켜야 할 핵심 원칙

### 데이터 흐름

쇼핑몰 API → 채널별 조회 커넥터 → 별도 수집 워커의 검증·정규화 → PostgreSQL → 서버 조회 서비스 → 대시보드·알림.

화면은 쇼핑몰 API를 직접 호출하지 않고 DB의 최신 성공값을 읽습니다. 수집 실패 시 기존 값을 유지하고 마지막 성공·최근 실패 시각 및 오래된 데이터 상태를 함께 표시합니다.

### 재고 의미 구분

	<tr><td>값</td><td>의미</td><td>처리 원칙</td></tr>

정상 수량 0, 첫 조회 실패, 성공 후 실패, 미지원, 재고 관리 미사용, 지원 여부 미확인을 각각 구분합니다. 실패·빈 응답·누락 필드를 0으로 바꾸지 않습니다. 값 상태·최근 조회 상태·신선도·live/fixture 출처를 별도로 관리합니다.

### 식별·매핑

- 상품명이 아니라 내부 SKU와 원본 옵션 ID로 연결합니다.
- 같은 외부 ID가 다른 계정에 있어도 충돌하지 않도록 모든 식별 키에 계정 범위를 포함합니다.
- 쿠팡 vendorItemId, 스마트스토어 옵션 ID, ESM 마스터/사이트 상품번호와 옵션 식별자를 보존합니다.
- 자동 연결은 후보만 제안하고 운영자가 확정합니다. 미연결 옵션도 원본 데이터를 유지합니다.
- 주문은 행별 수량·상태를 보존하고 취소·부분 반품·교환은 별도 클레임으로 관리합니다.

## 5. 단계별 작업 체크리스트

### S0. 계정·API 승인·운영 환경 준비

**목표:** 실제 조회에 필요한 조건과 채널별 준비 상태를 파악합니다. **병행:** S1 개발 환경 준비.

- [ ] 판매자 계정 수·판매자 ID·상품/옵션 수·일 주문량·내부 SKU 현황 조사.
- [ ] 스마트스토어 애플리케이션과 상품·주문 조회 API 그룹 권한 확인.
- [ ] 쿠팡 vendorId·Access/Secret Key, 판매자배송·RG 조회 권한 확인.
- [ ] G마켓·옥션 판매자 ID·ESM+ 마스터 ID·서비스 URL·매출/개발 일정 자료 준비 및 API 신청·승인 상태 기록.
- [ ] 11번가 판매자 승인·Seller API 가입·키·로그인 개발가이드 접근 확인.
- [ ] 수집 서버의 고정 발신 IP 확보 및 채널별 허용 등록 확인.
- [ ] 키·토큰은 서버 비밀 저장소에 등록하고 만료·마지막 호출·권한 상태만 기록.
- [ ] 판매자센터 대조용 정상/0/미사용 재고·신규/변경 주문·클레임 샘플 선정.

**완료 기준:** 계정별 사용 가능/승인 대기/미신청/미확인과 지원되는 조회 범위가 정리됩니다. 키·승인이 없는 채널은 fixture 단계만 진행하고 실제 연동 검증은 미완료로 남깁니다.

**목표:** Windows·macOS·Linux에서 같은 소스와 버전으로 개발할 기반을 만듭니다. **선행:** 개발 규칙과 버전 조합 검토.

- [ ] Next.js 15·React 19·TypeScript 앱 초기화, Tailwind·shadcn·Zustand·RHF·Zod 설정.
- [ ] Node 24 LTS를 공통 후보로 검토하고 pnpm·Prisma·PostgreSQL과 호환되는 정확한 버전 고정.
- [ ] package.json·pnpm-lock.yaml·Node 버전 파일·코드 검사/포맷 설정 구성.
- [ ] .env.example·환경변수 검증·기본 fixture 모드·비밀값 제외 설정 작성.
- [ ] Compose로 개발 PostgreSQL 실행, 개발 DB만 대상으로 초기화하는 공통 도구 구성. 스키마·마이그레이션·seed 내용은 S2에서 구현.
- [ ] OS별 경로·대소문자·줄바꿈·셸 차이를 처리하고 공통 실행 명령 작성.
- [ ] Git 초기화와 공유 준비, 저장소 범위 결정 후 GitHub 생성/업로드 절차 수행. 실제 키·주문 개인정보·DB 백업·node_modules·.next는 제외.
- [ ] 관리자/조회자 로그인·서버 권한 경계 구성, 웹과 수집 워커 실행 분리.
- [ ] Windows/macOS/Ubuntu 기본 CI 구성, DB 서비스 통합 검증은 별도 Ubuntu job으로 분리. 앱·fixture·DB 기능이 생기는 단계에서 해당 검증 추가.

**완료 기준:** 기본 앱과 공통 명령이 동작하고 버전·설치 절차가 기록됩니다. 다른 OS 지원 완료는 해당 환경에서 설치·빌드·DB·웹·워커 실행을 실제 재현한 뒤 표시합니다.

### S2. DB·SKU·상품/주문 식별 모델

**목표:** 모든 채널을 공통 데이터 구조로 저장합니다. **선행:** S1.

- [ ] 조직·사용자·역할·채널 계정·공유 자격증명·기능 지원 모델.
- [ ] 내부 SKU·상품·옵션·ESM 마스터/사이트 상품번호·매핑 후보/승인 이력.
- [ ] 성공 재고 관측과 현재값 포인터, 조회 상태·신선도·출처 분리.
- [ ] 주문·주문 행·상태 이벤트·취소/반품/교환·부분 수량 모델.
- [ ] 수집 실행·페이지·체크포인트·영속 작업·리스·원본 보관/만료 모델.
- [ ] 알림 규칙·발생/해결 이력·중복 억제·감사 기록.

### S3. 공통 커넥터·수집·복구 기반

**목표:** 채널을 추가해도 공통 수집·검증·화면을 재사용합니다. **선행:** S2.

- [ ] 상품/옵션·재고·주문·클레임 조회 인터페이스와 supported/unsupported/unverified 기능 지원 관리.
- [ ] 원본 응답 Zod 검증 → 정규화 → 공통 Zod 검증 → 저장 구현.
- [ ] 전체 페이지 처리, cursor 반복 탐지, API 기간 제한에 맞춘 범위 분할.
- [ ] 계정/공유 제한 그룹별 요청 예산, 429·재시도·권한 오류·시간초과 처리.

## 7. GitHub에서 받아 다른 OS에 적용하는 목표 절차

**같은 스택을 사용할 수 있지만 다운로드만으로 도구·DB·키가 자동 설정되지는 않습니다.** 아래는 구현 후 제공할 절차이며 현재 실행 명령/설정 파일이 준비된 상태는 아닙니다.

1. 지원되는 Git·지정 Node·지정 pnpm·Docker/DB 도구 설치.
2. GitHub 저장소 clone 또는 소스 다운로드.
3. .env.example 기반 로컬 환경 작성, 기본 fixture 모드 유지.
4. 잠금 파일 기반 의존성 재설치와 해당 환경에서 필요한 client 생성.
5. PostgreSQL 실행·준비 확인·개발 마이그레이션·비식별 seed.
6. 공통 명령으로 웹·워커 실행, 타입·린트·빌드·기능 검증.

- 저장소에 포함: 코드, package.json, pnpm-lock.yaml, 버전/검사 설정, Compose, Prisma 스키마/마이그레이션, fixture/seed, .env.example, 설치 안내, CI.
- 제외: 실제 API 키·토큰·.env, 실주문 원본·DB 데이터/백업, node_modules·.next·로그.
- Node 버전 파일은 기준 기록이며 실제 설치/전환을 도구·CI에서 확인합니다.
- macOS Apple Silicon은 ARM64, 일반 Windows/Linux x64 등 CPU 차이를 고려합니다. 설치 결과·네이티브 모듈·빌드 폴더를 OS 간 복사하지 않습니다.
- GitHub Actions의 PostgreSQL 서비스 컨테이너 검증은 Linux job에서 수행합니다. OS 매트릭스만 통과했다고 각 PC의 Docker까지 검증한 것으로 표시하지 않습니다.
- 각 PC의 실제 API 권한·발신 IP는 별도입니다. 운영 계정 수집은 승인된 서버에서 수행하고 로컬 기본값은 fixture/수집 비활성으로 둡니다.
