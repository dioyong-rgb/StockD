## 1. 계정·앱·호출 IP 준비
**사전 조건:** 내 스토어를 관리할 수 있는 계정과 API 호출 서버를 확보하라.

1. 해당 계정으로 커머스API센터에 로그인하라.
2. 계정별 등록 메뉴와 사용 가능 여부를 실제 화면에서 확인하라.
3. 내 스토어용 애플리케이션을 등록하라.
4. 애플리케이션 활성 상태를 확인하라.
5. 사용할 상품·주문 API 그룹의 권한을 확인하라.
6. 실제 요청 서버의 발신 IPv4 주소를 확인하라.
7. API 호출 IP 입력란에 해당 주소를 입력하라.
8. 추가 버튼을 눌러라.
9. 저장하라.

**확인 기준:** 대상 스토어·앱 활성 상태·필요 API 그룹·등록 IP가 실제 호출 환경과 일치해야 한다.

**불일치 시 조치:** 앱·권한·IP 중 미확인 조건이 있으면 해당 조회를 중단하라. 조건을 보완한 후 재개하라.

**참고:** 네이버는 2024-09-11부터 앱 신규 등록·수정 시 API 호출 IPv4 등록을 필수로 안내한다. StockD의 고정 발신 IPv4 사용은 등록 주소 변경을 줄이기 위한 운영 권장 사항이다.

**근거:** [커머스API센터](https://apicenter.commerce.naver.com/ko) · [API 그룹 권한](https://apicenter.commerce.naver.com/docs/restriction) · [API 호출 IP 등록 안내](https://help.sell.smartstore.naver.com/faq/content.help?faqId=15538)

## 2. 서버 서명 생성 및 토큰 발급
**사전 조건:** 작업 1의 앱·권한·IP 조건을 충족하라. 앱 ID와 시크릿을 서버 비밀 저장소에 등록하라.

1. 서버 시계를 확인하라.
2. 현재 시각을 Unix 밀리초 timestamp로 생성하라.
3. 앱 ID·timestamp·시크릿으로 bcrypt 해시를 생성하라.
4. 해시 문자열을 Base64로 인코딩하라.
5. 생성한 client_secret_sign을 사용하여 OAuth2 Client Credentials 토큰 발급 요청을 전송하라.
6. 발급된 액세스 토큰을 서버에서 관리하라.
7. 조회 요청의 Authorization 헤더에 Bearer 토큰을 설정하라.

**확인 기준:** 토큰 발급 응답의 성공 여부와 토큰 존재를 확인하라. 이어서 허용된 상품·주문 조회가 성공하는지 확인하라. 토큰 발급만으로 모든 API 권한을 확인했다고 판정하지 말라.

**불일치 시 조치:** 앱 ID·시크릿·timestamp·서명 구성·앱 상태·등록 IP를 대조하라. 비밀값을 화면이나 작업 기록에 출력하지 말라. 원인을 조치한 후 재개하라.

<details>
<summary>인증 구성 세부사항</summary>
	- 기본 주소: `https://api.commerce.naver.com/external`
	- 토큰 발급: `POST /v1/oauth2/token`
	- bcrypt 비밀번호: `client_id + "_" + timestamp`
	- bcrypt salt: `client_secret`
	- `client_secret_sign`: bcrypt 해시 문자열을 UTF-8 바이트로 변환한 뒤 Base64 인코딩하라.
	- API 조회 헤더: `Authorization: Bearer {access_token}`
	- 위 중괄호는 치환 위치를 나타낸다. 실제 토큰을 문서에 붙여 넣지 말라.
</details>

**근거:** [네이버 인증·서명·Bearer 사용 규칙](https://apicenter.commerce.naver.com/docs/auth)

## 3. 상품 및 옵션 식별자 확보
**사전 조건:** 해당 스토어의 상품 조회 권한과 서버 토큰을 확인하라.

1. 상품 목록 조회 API를 호출하라.
2. 요청·응답 사양의 페이지 조건에 따라 전체 목록을 조회하라.
3. 응답의 contents[].originProductNo를 보존하라.
4. 원상품 번호로 상품 상세를 조회하라.
5. 옵션이 있으면 실제 옵션 ID와 판매자 관리 코드를 보존하라.
6. 스토어·원상품 번호·옵션 ID를 내부 SKU 연결 후보와 함께 기록하라.
7. 운영자가 상품·옵션을 대조한 후 내부 SKU 연결을 확정하라.

**확인 기준:** 원상품과 실제 판매 옵션이 대응해야 한다. 상품명이나 판매자 관리 코드만으로 서로 다른 옵션을 합치지 말라.

**불일치 시 조치:** 식별자 또는 옵션 대응이 불명확하면 연결 대기로 기록하라. 미확인 옵션을 다른 상품에 임의로 연결하지 말라.

<details>
<summary>상품 조회 경로</summary>
	- 목록: `POST /v1/products/search` · 응답 식별자 `contents[].originProductNo`
	- 상세: `GET /v2/products/origin-products/{originProductNo}`
	- 실제 상세 응답의 옵션 유형·옵션 ID·`sellerManagerCode`를 확인하라. 반환되지 않은 필드를 만들어 채우지 말라.
</details>

**근거:** [상품 목록 조회](https://apicenter.commerce.naver.com/docs/commerce-api/current/search-product) · [원상품 상세 조회](https://apicenter.commerce.naver.com/docs/commerce-api/current/read-origin-product-product) · [상품·옵션 구조](https://apicenter.commerce.naver.com/docs/commerce-api/current/schemas/%EC%9B%90%EC%83%81%ED%92%88-%EC%A0%95%EB%B3%B4-%EA%B5%AC%EC%A1%B0%EC%B2%B4)

## 4. 상품·옵션 재고 판독
**사전 조건:** 작업 3의 상품·옵션 식별자를 확인하라. 조회한 옵션 유형을 구분하라.

1. 해당 상품 또는 옵션의 stockQuantity를 읽어라.
2. 수량을 채널의 판매 재고 값으로 기록하라.
3. 표준형 옵션이면 useStockManagement 설정을 함께 확인하라.
4. 수량과 재고 관리 여부를 각각 보존하라.
5. 마지막 성공 시각과 최근 시도 시각을 함께 기록하라.

**확인 기준:** 재고 관리가 확인된 정상 응답의 수량 0은 품절로 구분하라. 조회 실패·미제공·관리 여부 미확인은 별도 상태로 구분하라.

**주의:** 표준형 옵션의 useStockManagement가 미입력 또는 false이면 문서상 수량이 9,999로 설정된다. 이 값을 실제 보유 재고로 표시하지 말라. 수량 9,999만으로 관리 여부를 판단하지 말라. 이 규칙을 모든 옵션 유형에 일괄 적용하지 말라.

**불일치 시 조치:** 설정을 확인할 수 없으면 재고 관리 여부를 미확인으로 기록하라. 조회 실패 시 이전 성공 수량과 시각을 유지하라. 첫 실패에는 확인된 수량이 없음을 표시하라.

**근거:** [stockQuantity·표준형 옵션·useStockManagement 정의](https://apicenter.commerce.naver.com/docs/commerce-api/current/schemas/%EC%9B%90%EC%83%81%ED%92%88-%EC%A0%95%EB%B3%B4-%EA%B5%AC%EC%A1%B0%EC%B2%B4)

## 5. 변경된 상품주문 ID 수집
**사전 조건:** 주문 조회 권한을 확인하라. 변경 시각 기준의 조회 시작·종료 범위를 정하라.

1. 해당 범위의 변경 상품주문 목록을 조회하라.
2. 응답의 상품주문 ID와 원본 변경 정보를 보존하라.
3. more가 있으면 다음 페이지 조건을 구성하라.
4. more.moreFrom을 다음 요청의 lastChangedFrom에 전달하라.
5. more.moreSequence를 다음 요청의 moreSequence에 전달하라.
6. 같은 목표 종료 범위를 유지하면서 more가 없어질 때까지 조회하라.
7. 수집한 ID를 작업 6의 주문 상세 조회로 넘겨라.

**확인 기준:** 페이지당 최대 300개라는 제한을 적용하라. 요청한 범위의 모든 페이지를 확인하라. 신규 결제와 기존 주문 상태 변경을 구분하라.

**불일치 시 조치:** 페이지가 실패하거나 다음 조건이 반복되면 해당 범위를 미완료로 기록하라. 기존 성공 데이터를 보존하고 누락 범위를 재조회하라. 미완료 범위를 수집 완료 시각으로 확정하지 말라.

<details>
<summary>변경 주문 조회 경로 및 페이지 규칙</summary>
	- `GET /v1/pay-order/seller/product-orders/last-changed-statuses`
	- 다음 페이지는 `more.moreFrom → lastChangedFrom`, `more.moreSequence → moreSequence`로 구성하라.
	- 응답 최대 개수는 300개이며 `limitCount`를 설정한 경우 해당 설정에 따라 조회된다.
	- 종료 시각 유지와 전체 수집 후 완료 시각 확정은 StockD의 수집 누락 방지 설계다.
	- 변경 목록의 건수는 신규 주문 건수가 아니다. 상세의 식별자·상태로 신규 주문과 변경을 구분하라.
</details>

**근거:** [변경 상품주문 조회·300개 제한·more 규칙](https://apicenter.commerce.naver.com/docs/commerce-api/current/seller-get-last-changed-status-pay-order-seller)

## 6. 주문 상세 및 클레임 확인
**사전 조건:** 작업 5에서 수집한 상품주문 ID와 조회 권한을 확인하라.

1. 상품주문 ID를 한 요청당 최대 300개로 나누어라.
2. 각 묶음의 상품주문 상세를 조회하라.
3. 상품주문 ID·상품·옵션·수량·원본 주문 상태를 보존하라.
4. 취소·반품·교환의 클레임 유형과 원본 상태를 구분하여 기록하라.
5. 같은 상품주문 ID가 다시 수집되면 기존 데이터를 갱신하라.
6. 중복 수집으로 주문 건수가 증가하지 않는지 확인하라.
7. 작업 5의 전체 페이지와 필요한 상세 조회가 완료된 범위만 완료로 기록하라.

**확인 기준:** 요청한 상품주문 ID와 반환된 상세를 대조하라. 주문 상태와 클레임 상태를 각각 보존하라. 목록에 나타났다는 이유만으로 클레임 완료를 판정하지 말라.

**불일치 시 조치:** 상세가 누락되거나 상태를 해석할 수 없으면 해당 주문을 확인 대기로 기록하라. 누락된 필드를 완료 상태 또는 수량 0으로 채우지 말라. 원본 응답과 스마트스토어 화면을 대조하라.

<details>
<summary>주문 상세 조회 경로</summary>
	- `POST /v1/pay-order/seller/product-orders/query`
	- 요청의 상품주문 ID는 한 번에 최대 300개다.
	- 이 POST 요청은 주문 조회다. 발주 확인·발송·취소 승인 등의 처리 API를 대신 호출하지 말라.
	- 동일 ID 갱신과 중복 수집 허용은 StockD의 데이터 저장 설계다.
</details>

**근거:** [상품주문 상세 조회 및 ID 제한](https://apicenter.commerce.naver.com/docs/commerce-api/current/seller-get-product-orders-pay-order-seller) · [변경 주문의 주문·클레임 상태](https://apicenter.commerce.naver.com/docs/commerce-api/current/schemas/%EB%B3%80%EA%B2%BD-%EC%83%81%ED%92%88-%EC%A3%BC%EB%AC%B8-%EC%A0%95%EB%B3%B4-%EA%B5%AC%EC%A1%B0%EC%B2%B4)

## 7. 호출 제약 및 오류 처리 확인
**사전 조건:** 서버 통신과 앞선 조회 작업의 응답 처리 구성을 확인하라. 호출 제약은 첫 조회부터 적용하라.

1. TLS 1.2 이상으로 통신하라.
2. 호출한 API와 인증 앱별 제한을 확인하라.
3. 응답의 RateLimit·Quota 헤더를 확인하라.
4. 429가 발생하면 즉시 반복 요청을 중단하라.
5. 해당 한도와 회복 조건에 맞게 호출 빈도를 조정하라.
6. 401과 GW.AUTHN이 발생하면 토큰 만료 가능성을 포함하여 인증 상태를 점검하라.
7. 실패한 조회를 재고 0 또는 수집 완료로 표시하지 않는지 확인하라.

**확인 기준:** API별 응답 헤더와 오류 코드에 따라 조치해야 한다. 공통 고정 호출 횟수를 임의로 가정하지 말라. 토큰 재발급·재시도는 횟수와 대기 기준을 정해 적용하라.

**불일치 시 조치:** 권한·IP·앱·토큰 오류의 원인이 남아 있으면 해당 조회를 중단하라. 무한 재발급·무한 재시도를 수행하지 말라. 기존 성공값을 유지하고 실패 시각과 비밀값을 제외한 오류를 기록하라.

<details>
<summary>제약 확인 항목</summary>
	- 속도 제한 헤더: `GNCP-GW-RateLimit-*`
	- 할당량 헤더: `GNCP-GW-Quota-*`
	- 429 오류 코드: `GW.RATE_LIMIT`, `GW.QUOTA_LIMIT`
	- 인증 오류가 모두 만료를 뜻하는 것은 아니다. HTTP 상태·오류 코드·앱 조건을 함께 대조하라.
	- 재시도 횟수·대기 기준·기존 성공값 보존은 StockD 운영 설계다. 실제 제한값은 응답과 최신 공식 문서를 사용하라.
</details>

**근거:** [TLS·API 그룹·호출 제한·헤더](https://apicenter.commerce.naver.com/docs/restriction) · [토큰 및 인증 오류 처리](https://apicenter.commerce.naver.com/docs/auth)

## 8. 기능 시험 및 완료 판정
**사전 조건:** 적용 기능의 앞선 조회 작업을 완료하라. 스마트스토어 대조용 상품·옵션·주문·클레임을 선정하라.

1. 같은 상품·옵션·기준시각의 수량과 관리 설정을 스마트스토어 화면과 대조하라.
2. 같은 기간의 주문 ID·주문 행·수량·클레임 상태를 대조하라.
3. 상품 목록·변경 주문의 전체 페이지와 주문 상세 묶음을 확인하라.
4. 재고 0·조회 실패·누락·미제공·관리 미확인이 구분되는지 확인하라.
5. 작업자·작업일·대조 범위·불일치·조치 결과를 기록하라. 비밀값과 주문 개인정보는 기록에 포함하지 말라.
6. 검증한 기능에 한해 실제 연동 완료를 판정하라.

**합격 기준:** 해당 기능의 인증·권한·조회·전체 페이지·스마트스토어 대조가 확인되고, 수량 의미와 오류 표시가 일치해야 한다.

**불합격 시 조치:** 불합격 기능은 미연결 또는 검증 대기로 유지하라. 원인을 조치한 후 해당 시험을 반복하라. 미확인 기능을 합격 범위에 포함하지 말라.

### 작업 완료 기록
실제 작업 증거가 확보된 항목만 표시하라. 현재 모든 항목은 미수행이다.

- [ ] 대상 스토어·앱 활성·API 그룹·등록 IPv4를 확인했다.
- [ ] 서버 서명·토큰 발급과 상품·옵션 식별을 확인했다.
- [ ] 재고 관리 여부와 변경 주문·상세 조회의 전체 범위를 확인했다.
- [ ] 스마트스토어 대조와 오류·재고 0 구분을 확인했다.
- [ ] 완료 기능과 미확인 기능의 범위를 기록했다.

## 이상 발생 시 공통 조치
- 인증·권한·IP 문제: 해당 조회를 중단하라. 원인을 확인한 후 재개하라.
- 호출 제한 초과: 반복 요청을 중단하라. 제한 종류와 회복 조건에 맞게 호출 빈도를 조정하라.
- 일부 페이지·상세 실패: 완료 범위를 확대하지 말라. 마지막 성공값을 보존하고 미완료 범위를 재조회하라.
- 식별자·수량·상태 불일치: 해당 데이터를 성공값으로 덮어쓰지 말라. 원본 응답과 스마트스토어 화면을 대조하라.

## 근거 및 기록 관리
원문은 위의 네이버 스마트스토어 API 연결 페이지다. 공식 근거는 각 작업의 링크를 사용하라. 인증·호출 제약·호출 IP·상품 조회 경로·재고 관리 정의·변경 주문 페이지 규칙·주문 상세 제한은 2026-10-04 공식 문서와 다시 대조했다. 실제 작업 전 각 링크의 최신 요청·응답 계약을 확인하라.

고정 발신 IP 권장, SKU 연결 확인, 기존 성공값 보존, 수집 완료 시각 관리와 재시도 기준은 StockD의 운영 설계다. API의 공식 필수 조건과 구분하여 적용하라.

현재 앱 자격증명 등록·실제 API 호출·스마트스토어 대조는 수행하지 않았다. 문서의 절차와 실제 작업 완료를 구분하여 기록하라.
